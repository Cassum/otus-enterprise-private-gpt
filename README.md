# Enterprise Private GPT

Локальный корпоративный чат-бот (RAG) по внутренней базе знаний. Отвечает
**только** по загруженным документам, не обращаясь к внешним API и не отправляя
данные за пределы машины: LLM, эмбеддинги и векторная база работают локально.

База знаний для демонстрации — [Ultralytics Handbook](https://handbook.ultralytics.com/)
(корпоративные политики, онбординг, финансы, безопасность).

## Возможности

- Семантический поиск по документам (ChromaDB + локальные эмбеддинги).
- Генерация ответа локальной LLM по найденному контексту.
- Ограничение системного промпта: если ответа нет в базе — ассистент сообщает об этом.
- Чат-интерфейс на Streamlit.
- Набор из 22 оценочных вопросов и скрипт для сравнения размеров чанков.

## Архитектура

```
data/docs/en/*.md
      │  MarkdownTextSplitter (chunk_size=1000, overlap=100)
      ▼
   чанки + метаданные (file, part_id)
      │  nomic-embed-text-v2-moe (Ollama)
      ▼
   ChromaDB (persistent, ./data/chromadb)
      │  similarity search, top-K
      ▼
 вопрос ──► эмбеддинг ──► retrieval ──► system prompt {context} ──► qwen2.5:3b (Ollama) ──► ответ
                                                                          │
                                                                    Streamlit UI
```

| Слой | Реализация | Почему |
|------|------------|--------|
| LLM | `qwen2.5:3b` через Ollama | небольшой вес, работает на CPU, понимает русский |
| Embeddings | `nomic-embed-text-v2-moe` через Ollama | многоязычная MoE-модель, лёгкая (~1 ГБ) |
| Векторная БД | ChromaDB (persistent) | локальная, хранит метаданные, простой API |
| Чанкинг | `MarkdownTextSplitter` | учитывает структуру Markdown-документов |
| Интерфейс | Streamlit | минимум кода, чат «из коробки» |

### Структура проекта


## Запуск

Требования: Python 3.13+, [uv](https://docs.astral.sh/uv/) и установленный
[Ollama](https://ollama.com/).

```bash
# 1. Скачать локальные модели
ollama pull qwen2.5:3b
ollama pull nomic-embed-text-v2-moe:latest

# 2. Установить зависимости
uv sync

# 3. Построить векторную базу из документов
uv run python store_data_in_chroma.py

# 4. Запустить интерфейс
uv run streamlit run chat.py
```

Альтернатива без uv:

```bash
pip install -r requirements.txt
python store_data_in_chroma.py
streamlit run chat.py
```

Проверить пайплайн из консоли без интерфейса:

```bash
uv run python assistant.py
```

## Конфигурация

Все параметры в `config.yaml`:

```yaml
chunking:
  method: "markdown"
  chunk_size: 1000
  chunk_overlap: 100

llm:
  model: "qwen2.5:3b"
  base_url: "http://localhost:11434"
  temperature: 0.1

chromadb:
  db_path: "./data/chromadb"
  collection_name: "docs"
  embedding_model: "nomic-embed-text-v2-moe:latest"

ingest:
  data_path: "./data/docs/en"
  batch_size: 100
```

`config.py` валидирует этот файл через pydantic, поэтому опечатка в ключе
приводит к понятной ошибке загрузки, а не к «тихому» дефолту.

## Как работает RAG-пайплайн

1. Вопрос векторизуется той же моделью эмбеддингов, что и документы.
2. `assistant.py:41 prepare_context` достаёт top-K релевантных чанков из ChromaDB
   (по умолчанию `collection.query`, K=10) вместе с метаданными `file` и `part_id`.
3. Чанки склеиваются в контекст, который подставляется в системный промпт:

   > Ты корпоративный ассистент по внутренней базе знаний Ultralytics.
   > Отвечай на вопрос пользователя ТОЛЬКО опираясь на следующий контекст: {context}.
   > Если ответа в контексте нет, скажи, что не знаешь.

4. Промпт уходит в локальную `qwen2.5:3b` через Ollama, ответ возвращается в UI.

## Подбор размера чанка

Скрипт `test_different_chunking.py` прогоняет один и тот же набор из 22 вопросов
по индексам, построенным с разными `chunk_size`, и сохраняет ответы, время
генерации и эталоны в `test_different_chunking_report.yaml`.

| chunk_size | Чанков | Характер ответов | Средняя latency |
|-----------:|-------:|------------------|-----------------|
| 100 | 18 703 | обрывочные, часть фактов теряется | 9–30 с |
| 200 | 3 462 | лучше, но нестабильно | 17–27 с |
| 500 | 1 091 | в основном верно | 20–50 с |
| **1000** | **509** | **верно, включая конфликтный вопрос** | **55–85 с** |
| 2000 | 249 | деградация (теряются детали) | ~120 с |
| 5000 | 111 | галлюцинации, «зацикливание» текста | 190–290 с |

Вывод: слишком мелкие чанки теряют контекст, слишком крупные (2000+) перегружают
контекстное окно и провоцируют повторы и выдумки. Для 3B-модели компромисс —
**`chunk_size = 1000`** (установлен в `config.yaml`, индекс в `data/chromadb`).
Изменение `chunk_size` применяется только при **пересборке** индекса.

## Примеры ответов

Примеры ниже — реальные ответы системы на индексе `chunk_size=1000`
(полные результаты — в `test_different_chunking_report.yaml`).

### 1. Запрос по базе

> **Q:** Сколько дней PTO получает новый сотрудник в первый год работы?
>
> **A:** По контексту, новый сотрудник получает 25 дней PTO в первый год работы.
> Эти 25 дней включают базовое количество PTO (24 дня) плюс 1 день за день рождения.

Эталон: _25 дней в год: 24 гибких дня + 1 день в честь дня рождения._
Совпадает.

### 2. Запрос вне базы

> **Q:** Какая зарплатная вилка у Junior Data Scientist в Ultralytics?
>
> **A:** В контексте, который вы предоставили, нет конкретной информации о
> зарплатной вилке для Junior Data Scientist в Ultralytics. Для получения этой
> информации рекомендуется обратиться напрямую к HR или финансовому отделу компании.

Ожидаемое поведение: в базе нет зарплатных вилок — ассистент отказывается
выдумывать.

### 3. Конфликт с внешними знаниями LLM

Вопрос про clawback: общие знания модели подсказывают, что при увольнении деньги
обычно возвращают, но в регламенте Ultralytics условие другое — возврат только
при добровольном уходе.

> **Q:** Нужно ли возвращать $10,000 за релокацию, если сотрудника уволили
> (не по собственному желанию) через 6 месяцев?
>
> **A:** Если сотрудника уволили не по собственному желанию через 6 месяцев,
> то возврат $10,000 за релокацию не требуется. В релокационной политике указано,
> что возврат платежа применяется при "Voluntary Resignation" ...

Модель отдаёт приоритет контексту из базы, а не собственным знаниям.

## Анализ слабых мест и вывод о защите данных

**Плюсы локального стека**

- Все компоненты (LLM, эмбеддинги, БД) работают на машине; единственный сетевой
  адрес — `http://localhost:11434`. Данные не уходят в интернет.
- Модели скачиваются один раз (`ollama pull`), дальше система работает офлайн.
- Конфликтный тест показывает, что ассистент следует базе, а не «общим знаниям».

**Ограничения и трудности**

- **Latency на CPU.** 3B-модель генерирует ответ ~60–100 с (первый запрос дольше —
  загрузка модели в память). Для интерактива нужен GPU или модель поменьше.
- **Галлюцинации.** На крупных чанках (≥2000) ответы деградируют: повторы и
  выдуманные числа. Исправляется подбором `chunk_size` и уменьшением top-K.
- **Качество 3B-модели.** Иногда проскакивает смешение языков и самопротиворечия —
  заметно на многошаговых вопросах.
- **Prompt injection.** Системный промпт ограничивает ответы, но надёжной защиты
  от попыток «сломать» инструкцию нет.

**Надёжность защиты корпоративных данных**

Система действительно обеспечивает data residency: содержимое документов и
запросы не покидают хост, что закрывает главный риск публичных LLM.
Однако «локально» ≠ «безопасно»: для продакшена нужны аутентификация
пользователей, привязка Ollama только к localhost, шифрование диска,
разграничение доступа к коллекции и журналирование запросов.

## Оценка

`eval_questions.yaml` содержит 22 вопроса по 6 группам: точечные факты, данные в
таблицах, условия/пороги, многошаговые (multi-hop), суммаризация и negative-набор
(вопросы, ответов на которые в базе нет). Эталоны и источники указаны для каждого
вопроса — по ним можно вручную или автоматически сравнивать ответы.

## Ограничения воспроизведения

Каталог `data/chromadb/` не хранится в git (генерируется ингестом). Для запуска
на новой машине достаточно выполнить шаги из раздела «Запуск».
